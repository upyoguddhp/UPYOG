# egov-workflow-v2 migration notes

Audit-and-port: full commit history was reviewed to separate real HP customizations from noise (this directory's history is large - ~90 commits - but most are debug logging added-then-reverted, CORS tweaks that ended up converging with upstream's own no-CORS baseline, or test-only changes). The Java engine and models were wholesale-replaced with `UPYOG-master-Latest`, then the customizations below were re-applied.

## HP customizations found and ported

**Trade License workflow permission model** (already covered by egov-hrms's own migration - `WorkflowService.workflowTransition()` there calls into this service's `/process/_transition`). No changes needed here for that integration; it's a plain consumer of the standard transition endpoint.

**`role` column on `eg_wf_processinstance_v2`** (commit `a1c0e9cf05`): every process instance now records which role the acting user held when performing the transition. Ported to `ProcessInstance.java` (new `role` field, placed last so upstream's own DIGIT-standard field order is preserved), `WorkflowRowMapper.java`, `WorkflowValidator.java` (the actual capture logic - `roles.stream().filter(action.getRoles()::contains).findFirst().get()`), and the DDL migration (`ALTER TABLE eg_wf_processinstance_v2 ADD COLUMN role VARCHAR(128)` - column already existed in `hpupyog_5`, confirmed before porting). No query-builder change needed since the main search query is `SELECT pi.*` and 26 add the new column automatically. Adding this field to a `@AllArgsConstructor` class breaks any test that instantiates `ProcessInstance` positionally - fixed 13 call sites across `EnrichmentServiceTest.java`, `StatusUpdateServiceTest.java`, and `WorkflowValidatorTest.java` by appending `, null` (values taken directly from HP's own corresponding test-fix commit, `78fd943ad1`, not guessed).

**Workflow inbox / "next valid action" API** (commit `ef74fc35aa`, refined by three follow-up "fix"/"changes" commits): a new `POST /egov-wf/_action?businessId=...&tenantId=...` endpoint (`WorkflowInboxController` + `WorkflowInboxService` + `ValidActionResponce`) that, given a business object already in a workflow, returns which of its next actions the *calling user* is actually permitted to take (role-intersected) and whether its state is currently updatable - used by frontends to decide which action buttons to show without walking the full process history. Ported the final, already-refined state of these files (not the initial commit) directly from the fork, since the intermediate "fix"/"changes" commits were all part of the same continuous feature build. Required adding `@Builder`/`@AllArgsConstructor`/`@NoArgsConstructor` to `ProcessInstanceSearchCriteria.java` (for `WorkflowInboxService`'s `.builder()...build()` usage) and restoring a `RequestInfo requestInfo` field on it that upstream doesn't have (needed by the unauthenticated search endpoint below, which takes the whole body as this criteria object). The inbox service also treats a `SYSTEM` role like `CITIZEN` for cross-tenant visibility (commit `52eed1778d`) - ported.

**Two unauthenticated/citizen-facing search variants** (`WorkflowController.java`, commits `e4099ad0f7` + others): `POST /process/_searchWithOutAuth` and `POST /process/_search-pgr` (the latter takes `ProcessInstanceSearchCriteria` - including its own embedded `RequestInfo` - as the entire request body, no wrapper). Both ported verbatim.

**Global exception handling** (commit `8f0a77a380`): a whole `org.egov.wf.exception` package (`ErrorConstants`, `ErrorInfo`, `ServiceException`, `ServiceExceptionHandler`) absent from upstream, giving structured JSON error bodies (`{errorCode, errorMessage, errorDetails, timestamp}`) instead of default Spring error pages for validation failures, JDBC/SQL errors, and any uncaught exception. Ported with two required Boot 3 signature fixes: `ResponseEntityExceptionHandler`'s overridden `handleHttpMessageNotReadable`/`handleMethodArgumentNotValid` take `HttpStatusCode` in Spring 6, not the old `HttpStatus` (compile error otherwise). Verified this coexists correctly with `egov-tracer`'s own `ExceptionAdvise` `@ControllerAdvice` - confirmed live via multiple test requests that consistently returned this handler's error shape, not tracer's.

**Fuzzy business-ID search disabled** (commits `b52a0287a1` then `dd75eda60a`): HP first flipped `egov.wf.fuzzysearch.isFuzzyEnabled=false`, then a day later additionally commented out the actual `WorkflowQueryBuilder` code implementing it - the config flag alone apparently wasn't trusted, or this predates upstream's own toggle maturing. Since upstream's current code already gates the feature cleanly behind the same property, ported as **config-only**: `isFuzzyEnabled=false`, code left intact. Same behavior, none of HP's code churn.

**SLA escalation query - kept old formula, did not adopt upstream's** (`EscalationQueryBuilder.java`): this one is *not* an HP customization - the file has no HP-authored commits at all. But upstream's current version simplified `(now - createdtime - statesla) > threshold` down to `(now - createdtime) > threshold`, dropping the SLA-duration subtraction entirely. Given `criteria.getStateSlaExceededBy()`/`getBusinessSlaExceededBy()` exist specifically to mean "how far past the SLA deadline," and `EscalationService`'s only caller passes MDMS-configured escalation thresholds through this exact path, upstream's simplified version would escalate every record older than the raw threshold regardless of its actual per-state/per-service SLA - a likely regression. Restored the original DIGIT 2.5-era formula (still present, unmodified, in the fork) rather than following upstream here. Flagging this explicitly since it's a rare case of *not* taking upstream's version despite no HP commit backing the fork's side.

**`TLInterceptor.java` dropped**: dead code (never registered as a `HandlerInterceptor` anywhere), same class found and dropped during the egov-user migration too. Not ported.

## Config changes (`application.properties`)
- `egov.mdms.search.endpoint`: upstream defaults to `/mdms-v2/v1/_search` - would 404 in this workspace, since the mdms-v2 cutover means mdms-v2 now owns the `/egov-mdms-service` context path, not `/mdms-v2`. Set to `egov-mdms-service/v1/_search`, matching every other already-migrated service.
- `egov.user.host`, `egov.statelevel.tenantid`: stale `dev.digit.org`/`pb` defaults fixed to the local port and `hp`, same recurring pattern as every other service.
- `egov.wf.fuzzysearch.isFuzzyEnabled=false` (see above).

## Cross-cutting bugs found and fixed during verification (not egov-workflow-v2 defects)
Testing `/process/_search` end-to-end (which enriches assignee/assigner data via a call out to egov-user) surfaced three real, platform-wide bugs, none in this service's own code:
1. **`egov-user`'s `egov.enc.host` pointed at the wrong port** (`http://localhost:8083/`, colliding with egov-filestore) - traced via `git blame` to a copy-paste mistake introduced during *this session's own* egov-user migration commit (`44f6c610df`), not something HP did. Fixed on this branch and separately hotfixed directly on `main` (see follow-up commit) since it silently broke PII encryption/decryption for every user-touching service in the whole platform. Confirmed via `git blame`: the fork's original value was correctly `1234` before that commit changed it.
2. **`hpupyog_5` was missing a few `eg_user`/`eg_user_address` columns** the currently-migrated egov-user code expects (`eg_user.digilockerid`; `eg_user_address` didn't need `alternatemobilenumber`/`accountlockeddate`/`isdataprotectionaccepted`/house-address fields added - those already existed - but did need `status`, plus backfilling 299,098 existing address rows to `status='active'` since the enrichment query filters on it). Applied the corresponding DDL migrations directly to `hpupyog_5` (the exact SQL already checked into `egov-user/src/main/resources/db/migration/ddl/`, just never applied to this replica).

With both fixed, the full `_search` request pipeline (MDMS → workflow-v2's own DB → egov-user's `/user/_search` → egov-user's PII decrypt call → egov-enc-service → back through egov-user's SQL layer) now correctly reaches real business logic and fails only on a legitimate `401 Unauthorized` from egov-user when no real auth token is supplied - i.e. auth is correctly enforced, and everything ahead of it works.

## Verification performed (this session)
Started via `upyogctl start egov-workflow-v2` against `hpupyog_5`:
- Compiled clean after fixing the two Boot 3 `HttpStatusCode` signature mismatches and the 13 test call-sites broken by the new `role` field.
- `GET /health` → `200 {"status":"UP"}`.
- MDMS connectivity confirmed at startup (`BusinessServiceMasterConfig` fetched correctly, 26 business services returned).
- `POST /process/_count` (real `PGR` business ID, `hp.Amb` tenant) → `200`, correct count (`1`) - confirms the DB query layer (including the new `role` column via `SELECT pi.*`) works end-to-end.
- `POST /process/_search`, `/process/_search-pgr`, `/egov-wf/_action` (the new inbox endpoint) - all three correctly traverse the full cross-service pipeline described above and fail only on the expected `401` from egov-user given a synthetic RequestInfo with no real auth token. Getting an actual `200` from these would require a real login flow to mint a token, out of scope for this pass, but every layer up to and including egov-user's own SQL execution was proven reachable and correct.
- Custom `ServiceExceptionHandler` confirmed active throughout - every error response observed during testing used its `{errorCode, errorMessage, errorDetails, timestamp}` shape, not Spring's default or tracer's.

**Not yet verified**: an actual successful (`200`) transition/search with a real, valid auth token; the escalation endpoint (`/escalate/_search`) and its restored SLA formula against real data; `/process/_statuscount`; `/process/_nearingslacount`; business-service create/update/search.
