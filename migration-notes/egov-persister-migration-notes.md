# egov-persister migration notes

Audit-and-port, not wholesale replace - and a much narrower one than usual. `egov-persister` isn't just a generic engine; its `src/main/resources/` is a **central repository of persister config YAML files for dozens of business services** (property, PGR, trade license, HRMS, asset, community hall booking, NOC, tobacco licensing, echallan, feedback, rent-lease, advertisement, PG/Razorpay transactions, etc.). A wholesale replace would have silently deleted every one of those configs, since the service's `egov.persist.yml.repo.path` property is the master list of which YAMLs actually get loaded - any file not in that list (or not present at all) means its Kafka topic has no listener and writes for that business service just stop, with no error anywhere.

## What was actually replaced
Only the generic engine code and build files, after confirming via git history that none of them carry real HP logic customization (the only HP-authored touch across all 6 differing Java files was debug `log.info(...)` calls added to `PersistService.java` in commit `9c255dfcbf`, not a behavior change - not ported):
- `pom.xml` (Spring Boot 2.2.13 → 3.2.2, Java 8 → 17)
- `EgovPersistApplication.java`, `PersisterBatchConsumerConfig.java`, `PersisterConsumerConfig.java`, `StoppingErrorHandler.java`, `PersistService.java`, `Utils.java`
- `src/test/java/.../StoppingErrorHandlerTest.java` (had to be replaced too - it referenced the old `StoppingErrorHandler` API shape and failed to compile against the new one; no HP history on this file either)
- Removed `src/main/resources/backup/` entirely: two old YAML backups (`egov-workflow-v2-persister.yml`, `noc-persister.yml`) plus four stray `.java` files (`Column.java`, `ObjectCollection.java`, `ObjectInfo.java`, `TableInfo.java`) that were never compiled (sitting in a *resources* folder) and aren't referenced by `egov.persist.yml.repo.path` - dead weight, not migration-relevant.

## What was deliberately NOT touched
**All ~29 YAML config files were left exactly as they are in the fork.** Diffed every one against upstream first:
- **14 files have no upstream counterpart at all** (`advertisement-service.yml`, `asset-service.yml`, `community-hall-booking-service-persister.yml`, `echallan.yml`, `egov-workflow-v2-persister.yml`, `feedback-service.yml`, `mdms-persister.yml`, `noc-persister.yml`, `pet-registration-persister.yml`, `pgr-services-persister.yml`, `property-services-registry.yml`, `rent-lease-service.yml`, `tobacco-persister.yml`, `tradelicense.yml`) - pure HP additions, nothing to reconcile.
- **13 of the 15 files that exist in both are byte-identical** to upstream - no HP customization, no upstream fix to adopt either.
- **`egov-pg-service-persister.yml` differs substantially**: HP added `bill_id`, `user_uuid`, `additional_details` (JSONB), `consumer_code`, `created_by`/`last_modified_by`, `is_multi_transaction`, `receipt`, `txn_settlement_status`, `settlement_response` (JSONB), `razorpay_response` (JSONB) columns to `eg_pg_transactions`, plus a whole extra `TransactionDetails`/`eg_pg_transactions_details` persister block - matches the "Saved razorPay logs in eg_pg_transactions table" commit at the top of this directory's git history. Kept fork's version entirely.
- **`hrms-employee-persister.yml` differs**: this copy (the one actually loaded via `egov.persist.yml.repo.path`) already had `additionalDetail` correctly wired in, and turned out to be **more current** than the copy bundled in `business-services/egov-hrms/src/main/resources/config/hrms-employee-persister.yml` that got edited during the egov-hrms migration - that HRMS-side copy is not the live one; this one in egov-persister's own resources is. Left as-is (already correct); the two copies drifting apart is a pre-existing condition, flagged here rather than reconciled since fixing it means picking which copy is authoritative for two different repos' worth of history, out of scope for this pass.

## Config fix
`server.port` was `8083`, which collides with `egov-filestore` (also `8083` in this workspace). The gateway's already-migrated route for `/egov-persister/**` targets `8084` - fixed `server.port` to `8084` to match. (Separately, the gateway route's own `Path=/egov-persister/**` predicate doesn't line up with this service's real `/common-persist` context path from either fork or upstream - but the persister has no inbound HTTP consumers of its own to speak of, it's a pure Kafka-consumer service, so this pre-existing mismatch - inherited verbatim from the old zuul config during the gateway migration - isn't a functional blocker and wasn't chased further here.)

## Bug found and fixed: `application.yml`'s built-in mappings were all broken
Not an HP bug - **confirmed present in vanilla `UPYOG-master-Latest` too** (the file is byte-identical between fork and upstream). Every one of the 15 query mappings in `application.yml` (the generic "User Service" persister for `eg_user`/`eg_user_address`, plus marriage-registration, fee, demand/bill, and property-validation mappings) used the key `rootObject:` instead of `basePath:`, which is what `QueryMap.java`'s actual `@JsonProperty` expects - every other config file in this directory (26 of them) correctly uses `basePath`. Because YAML deserialization silently drops unknown keys, `basePath` stayed `null` for every mapping in this file, and any attempt to actually use one crashed with `NullPointerException: Cannot invoke "String.contains(...)" because "baseJsonPath" is null` deep in `PersistRepository.extractData()`. This has evidently gone unnoticed because none of these particular topics see real traffic in this deployment (user creation happens via egov-user's direct JDBC writes, not through this Kafka route). Fixed by renaming every `rootObject:` to `basePath:` in `application.yml` (also added the missing `$.` prefix to the two `Users.*` paths, matching the convention every other config in this directory already uses) and verified live (see below).

## Verification performed (this session)
Started via `upyogctl start egov-persister` against `hpupyog_5` and local Kafka:
- Compiled clean after fixing the stale test file.
- Subscribed successfully to every one of the ~65+ Kafka topics referenced across all 29 config files with zero startup errors.
- `GET /common-persist/actuator/health` → `200 {"status":"UP"}`.
- End-to-end persistence test: published a hand-built message to `egov.persist` (the User Service topic in `application.yml`, one of the ones fixed above) via `kafka-console-producer` - correctly landed a fully-populated row in `eg_user` (verified via `psql`, then cleaned up). Confirms both the `rootObject` → `basePath` fix and the generic Boot3-ported engine work correctly end-to-end, from Kafka consumption through JsonPath extraction to the parameterized SQL insert.

**Not yet verified**: the other 14 mappings in `application.yml` (marriage registration, fee, demand/bill, property-validation) beyond confirming they now have a non-null `basePath` - the fix is structurally identical for all of them, but only the User mapping was exercised live. Also not verified: any of the 14 HP-only YAML configs' actual runtime behavior (asset, NOC, tobacco, echallan, etc.) - these weren't touched, so no regression is expected, but none were live-tested with real traffic in this session; recommend spot-checking a couple as their owning services get migrated.
