# egov-hrms migration notes

Audit-and-port (not wholesale replace): full commit history for `business-services/egov-hrms` was reviewed to find genuine HP customizations, which were then re-applied on top of `UPYOG-master-Latest/business-services/egov-hrms` (Spring Boot 2.2.13 → 3.2.2, Java 8 → 17, `javax.*` → `jakarta.*`). Upstream also independently refactored `UserService` from a concrete class into an interface with a `DefaultUserService` implementation (selectable via `egov.hrms.user.service.qualifier`, alongside a new `IndividualService` alternative for the newer "individual" citizen-data service) - HP's customizations to the old `UserService.java` were ported onto the new `DefaultUserService.java`.

## HP customizations found and ported

**Trade License workflow integration** (commits `216ed9262b`, `4e7045628c`, `cb3d878f19`, `7faa54afa0` - substantial, ~700 lines): a whole feature absent from upstream. `POST /employees/workflow/_transition` forwards a workflow-transition request to `egov-workflow-v2`, then - for the `NewTL` (Trade License) business service specifically - directly runs raw JDBC `UPDATE`s against `eg_tl_tradelicense` to set `status` (and `licensenumber` on approval), bypassing the TL-services microservice entirely. Also enforces that a `TL_FIELD_INSPECTOR`/`TL_FIELD_SUPERINTENDENT` can only VERIFY/APPROVE applications in their own tenant. Ported: `WorkflowService.java`, contract classes (`ProcessInstance`, `ProcessInstanceRequest`, `ProcessInstanceResponse`, `Action`, `Document`, `State` - hand-rolled, matching the convention every other UPYOG service uses for workflow-v2 integration, since there's no shared library for this), the `TRADELICENCE_*` constants in `HRMSConstants.java`, `PropertiesManager`'s `wfHost`/`wfTransition` fields, `egov.wf.host`/`egov.wf.transition` in `application.properties`, and the controller wiring.

**`additionalDetail` JSONB field** (commit `c6856e5331`): arbitrary extra employee data. Ported to `Employee.java` (new `JsonNode additionalDetail` field), `EmployeeQueries.java` (SELECT column), `EmployeeRowMapper.java` (`fetchAdditionalDetailJson`, using `PGobject`), and both `INSERT INTO eg_hrms_employee` blocks in `hrms-employee-persister.yml`. The `additionaldetail JSONB` column already exists in `hpupyog_5` from prior production use; the DDL migration file was restored anyway for schema-history completeness (irrelevant either way - `.upyog.env` disables Flyway).

**Jurisdiction validation disabled** (commit `3e988f48ea`): `Employee.jurisdictions`' `@Valid @NotEmpty @Size` and `Jurisdiction`'s three `@NotNull`s are commented out, and `EmployeeValidator`'s call to `validateJurisdicton(...)` is commented out. Required jurisdiction data isn't reliably available in this deployment. Ported as-is (commented, not removed, matching HP's own style) since re-enabling without knowing why it was disabled risks breaking employee creation outright.

**Case-insensitive JSON binding + `username` rename** (commits `7cd35ed78c`, `af459276fb`): `DefaultUserService.userCall()` now sets `ACCEPT_CASE_INSENSITIVE_PROPERTIES` before converting egov-user's response, and the local `web.contract.User.userName` field/JSON property was renamed to `username`. Verified compatible: the already-migrated `egov-user` globally enables `ACCEPT_CASE_INSENSITIVE_PROPERTIES` on its inbound `MappingJackson2HttpMessageConverter` (`EgovUserApplication.java`), so it accepts either casing - this is a safe rename, not a fix for an actual incompatibility. Two builder-call sites needed updating for the field rename that weren't in the original commit's diff (`IndividualService.java` line ~205's `.userName(...)` builder call, since upstream added `IndividualService.java` after this rename happened in HP's history) - fixed to `.username(...)`.

**`@PostConstruct` internal-microservice-user hook disabled** (commit `9610201598`): ported as disabled, for two independent, verified reasons - (1) `internalMicroserviceRoleUuid` is only consumed when `decryption.abac.enable=true`, which is `false` in this deployment, so the hook is inert dead code regardless; (2) upstream's own implementation (still present in `DefaultUserService.initalizeSystemuser()`) has a latent bug: when no internal user is found it calls `createInternalMicroserviceUser(...)` but then still indexes into the same (still-empty) `users` list, throwing `IndexOutOfBoundsException` - since `@PostConstruct` failures abort Spring context startup entirely, upstream's own code would fail to start HRMS on any fresh/empty database, HP's involvement aside.

**Employee-code and password generation safety nets** (commit `0e19915286`/`3e988f48ea`, partially superseded): HP's original ad-hoc "skip password generation if the caller already supplied one" was superseded by upstream's own `egov.hrms.auto.generate.password` config flag (kept at its default `true`, per user decision - see below). The `RandomStringUtils.randomAlphanumeric(8)` fallback for an empty employee code (guards a potential NPE in `enrichUser()` if `idGenService.setIds()` ever fails to populate one) was ported forward as a harmless safety net.

**MDMS employee-type null-check** (commit `0e19915286`): `EmployeeValidator`'s employee-type check now guards against a null MDMS lookup result before calling `.contains(...)`. Ported.

## Decisions made with explicit user input this session
- **SMS notification on employee creation**: HP had `notificationService.sendNotification(employeeRequest, pwdMap)` commented out in `EmployeeService.create()`, with no explanation. User chose to **re-enable it** (matching upstream's default) rather than preserve HP's disabled state - left upstream's active call as-is, did not port the comment-out.
- **`egov.hrms.auto.generate.password`**: user chose **`true`** (upstream's own default), matching HP's original pre-hack behavior of always generating a password for new employees.

## New bug found and fixed during verification (MDMS data, not HRMS code)
Employee creation initially failed with an NPE in `EmployeeValidator.validateAssignments()` (`mdmsData.get(HRMSConstants.HRMS_MDMS_DEPT_CODE).contains(...)` on a null map) - not an HRMS defect, but a **pre-existing gap in the mdms-v2 data migration**: `common-masters.Department`/other masters had zero rows in `hpupyog_5`, even though the schema definition existed. Root cause: `master-config.json`'s `uniqueKeys: ['$.code', '$.tenantId']` for `Department` references a `tenantId` field that the actual JSON records never carry (they only have `name`/`code`/`active`) - the same general "declared unique key doesn't match the real record shape" bug class already found and fixed twice before (case-sensitivity for `ACCESSCONTROL-ROLEACTIONS.roleactions`, missing-tenant-scope for `DataSecurity.*`). Fixed in the migration script: when a declared unique key is exactly `tenantId` and the record doesn't carry that field, fall back to the record's actual tenant (already known from the outer directory walk) instead of skipping the row. Re-ran the migration scoped to `hp`, backfilling 16 previously-skipped rows including all `Department`/`Designation` codes. (210 rows across 13 other master codes are still skipped for the same "declared unique key absent from record" reason - out of scope for this pass, flagged for whoever next needs those specific masters.)

## Config changes (`application.properties`)
- `egov.filestore.host`, `egov.localization.host`, `egov.otp.host`, `egov.user.host`, `egov.idgen.host`: none of these property names have a matching global env var in `.upyog.env` (unlike `egov.mdms.host`, which matches `EGOV_MDMS_HOST` exactly and needed no change) - set directly to the local ports for each already-migrated/available service (8083, 8087, 8089, 8081, 8088).
- `parent.level.tenant.id`, `state.level.tenant.id`: stale Punjab-demo defaults (`pb`/`default`) fixed to `hp`, same recurring class of bug found across nearly every service so far.
- Added `egov.wf.host=http://localhost:8280` / `egov.wf.transition=/egov-workflow-v2/egov-wf/process/_transition` for the ported workflow feature.
- `egov.hrms.employee.app.link` left at its stale Punjab-demo URL (`mseva.lgpunjab.gov.in`) - only used to build a link embedded in the reactivation SMS body, not load-bearing. Flagged, not fixed (no known HP-actual URL to substitute).

## Verification performed (this session)
Started via `upyogctl start egov-hrms` against `hpupyog_5`:
- Compiled clean after fixing two mistakes made while porting (forgot to add `wfHost`/`wfTransition` fields to `PropertiesManager.java`; missed one `.userName(...)` → `.username(...)` builder call in `IndividualService.java`).
- `GET /egov-hrms/actuator/health` → `200 {"status":"UP"}`.
- `POST /employees/_search?tenantId=hp` → real production employee records returned correctly, including the ported `additionalDetail` JSONB field (e.g. `{"wards":[{"tenantId":"hp.Shahpur"}]}`) - proves the JSONB round-trip works end-to-end against real data.
- `POST /employees/workflow/_transition`: inspector verifying their own tenant's `NewTL` application → passes validation (200; the actual workflow-v2 call itself failed since that service wasn't running, handled gracefully by the existing try/catch, not a regression). Inspector attempting to verify a **different** tenant's application → correctly rejected with `400 WORKFLOW_PERMISSION_FAILED`. Both the allow and deny paths of the ported permission check are confirmed working.
- `POST /employees/_create`: full validation pipeline (department/designation/employee-type MDMS checks, jurisdiction skip, assignment date checks) passes cleanly and the request reaches `DefaultUserService.createUser()`'s real call to egov-user's `_createnovalidate` endpoint - confirms the `username` field rename and overall request shape are compatible with the already-migrated egov-user. The final encryption step failed only due to an unrelated, pre-existing stale process on this machine (a long-running egov-user instance pointing at a stale enc-service port from a much earlier session) - not an egov-hrms defect. Full create-to-success has not been verified end-to-end in this session; recommend re-testing once `replace/egov-user`, `replace/egov-idgen`, and `replace/egov-hrms` are all merged and started fresh together.

**Not yet verified**: `_update`, `_count`, reactivation flow (`sendReactivationNotification`), the `individualService` qualifier path (`IndividualService.java` - not HP's active configuration, `egov.hrms.user.service.qualifier=defaultUserService`), and key rotation via `/crypto/v1/_rotatekey` equivalents (n/a here, that's egov-enc-service).
