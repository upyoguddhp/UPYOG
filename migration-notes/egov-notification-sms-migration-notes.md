# egov-notification-sms migration notes

Audit-and-port, but of a different shape than most other services in this effort: this directory has 81 commits, and the overwhelming majority of the code is genuine, still-live HP business logic with **no upstream equivalent at all** - a full OTP-over-SMS orchestration layer (with its own calls into egov-user and egov-otp), a citizen-lookup-by-mobile-number flow, an SMS/mail "billing tracker" subsystem with its own Postgres tables and a resend scheduler, and a DB-backed SMS template store. Upstream's own `egov-notification-sms` is a much smaller, stateless "take a pre-built message and forward it to a gateway" service.

Given how little of the fork's code has an upstream counterpart to replace it with, a wholesale replace-then-port would have meant reconstructing almost the entire service from scratch. Instead this was an **upgrade-in-place**: kept the fork's existing class structure and business logic untouched, and applied only the Spring Boot 3.2.2 / Java 17 mechanical fixes needed to compile and run - using upstream's equivalent files purely as a reference for *how* to fix each Boot 3 break (httpclient5 migration pattern, `jakarta.*` namespace, etc.), never for their content.

## What's genuinely HP-only (no upstream equivalent)

- **OTP-over-SMS orchestration** (`SMSController./otp`, `SMSService.sendOtp`/`validateCitizen`): looks up the user via egov-user (by uuid or by mobile number), requests an OTP from egov-otp, resolves the `LOGIN-OTP` template from this service's own `eg_sms_template` table, and sends it - all before ever touching the low-level gateway layer. Upstream's `SMSService` is a single `sendSMS(Sms)` method; this fork's version is a completely different, larger interface (`sendOtp`, `sendSMS(SMSSentRequest)`, `validateCitizen`, `populateSMSRequest`). Left entirely as-is.
- **SMS/mail billing tracker** (`SmsTracker`, `NotificationMailTracker`, `SmsTrackerRepository`, `SmsProcessing`, `NotificationSmsSchedulerController`): a full store-and-forward subsystem for bill-related notifications, with its own `eg_notification_sms_tracker`/`eg_notification_mail_tracker` tables (flyway migrations already checked in), a resend counter, and `POST /send-sms` / `POST /resend-counter` endpoints for a scheduler to drive retries. Nothing like this exists upstream.
- **DB-backed SMS template store** (`SMSTemplateRepository`, `eg_sms_template` table) - upstream has no template concept at all; every message upstream sends is fully pre-built by the caller.
- **`/smsbounce/callback`** (`CallbackAPI`) - receives delivery-status callbacks from the SMS gateway and republishes them to Kafka via `Producer`, hashing the mobile number first (`HashService` from `enc-client`). Upstream has no bounce-handling at all.

## Real bug found and fixed during verification

**`SmsTrackerRepository.insert()` never generated a UUID.** Its sibling method two lines below, `insertMailTracker()`, does `tracker.setUuid(UUID.randomUUID().toString())` before building the insert params - `insert()` never did, and never had, going back to the single commit that introduced it. Since `eg_notification_sms_tracker.uuid` is a `NOT NULL PRIMARY KEY` with no default, every call to `POST /_create` failed with `DataIntegrityViolationException: null value in column "uuid"`. Fixed by adding the same `tracker.setUuid(UUID.randomUUID().toString());` line, matching the working sibling exactly. Confirmed fixed live (see verification below).

Separately, but not fixed (pre-existing behavior, not a migration regression): `SmsProcessing.processPendingSms()`/`processSmsForBill()` mark a tracker row's `sms_status` as sent successfully as soon as `smsService.sendSMS()` returns *without throwing* - but `BaseSMSServiceImpl.sendSMS()` silently returns (no exception) when a number is blacklisted or not whitelisted, so a blacklisted number's tracker row gets marked `sms_status=true` even though nothing was ever sent. This exists in the fork's original code untouched by this migration; flagging it here since it surfaced clearly during verification (see below).

## Boot 3 / Java 17 mechanical fixes applied

- **`pom.xml`**: Boot parent bumped 2.2.13 → 3.2.2, `java.version` 1.8 → 17, `lombok.version` → 1.18.22, artifact version → `2.9.0-SNAPSHOT` (matching every other migrated service). Added `spring-boot-starter-validation` and `httpclient5` (needed for the SSL fix below), switched `spring-boot-starter-data-jdbc` → `spring-boot-starter-jdbc` (matches the pattern already used by other migrated services with the same JdbcTemplate-only usage), dropped explicit versions on `spring-beans`/`spring-kafka`/`postgresql`/`flyway-core`/`aspectjweaver` so Boot's own dependency-management BOM supplies them, dropped the unused `services-common` dependency (no code reference, matches upstream's own absence of it), bumped `enc-client` to `2.9.0` and `tracer` to `2.9.0-SNAPSHOT` (matching every other migrated service), removed the `maven-pmd-plugin` block (matches upstream dropping it), and updated the two nexus repository URLs to upstream's `upyog-nexus.niua.org`.
  - **Important correction made during verification**: initially copied `flyway-core`'s explicit `<version>10.7.1</version>` from another already-migrated service's pom (`egov-hrms`) without checking it against Boot 3.2.2's own BOM. Flyway 10 split PostgreSQL support out into a separate `flyway-database-postgresql` artifact that isn't declared anywhere in this workspace; Boot 3.2.2's BOM deliberately still manages `flyway-core` at **9.22.3**, the last version with Postgres support bundled directly (confirmed against the BOM's own `pom.xml` and against `egov-otp`'s already-migrated pom, which correctly pins `9.22.3`). Removed the explicit version here so the BOM's `9.22.3` applies. **This same latent bug (an explicit `flyway-core:10.7.1` pin with no `flyway-database-postgresql` add-on) may already be present in other already-migrated services that copied the same pattern** (`egov-persister` on `main` was seen with this exact pin) - worth a follow-up audit if any of those services ever run Flyway against Postgres for real (in this workspace, `SPRING_FLYWAY_ENABLED=false` is set globally in `.upyog.env`, so the bug hasn't been visible locally).
- **`javax.*` → `jakarta.*`**: `javax.annotation.PostConstruct`/`javax.annotation.*` (application class, `BaseSMSServiceImpl`, `NICSMSServiceImpl`) and `javax.validation.*` (`SMSSentRequest`, `User`, `Otp`, `Token`, `UserSearchRequest`, `OtpRequest`, the Kafka contract `SMSRequest`). `javax.net.ssl.*` left untouched - that's JDK-standard, unaffected by the Boot/Spring split.
- **`@SafeHtml` removed from `Report.java`**: Hibernate Validator 8.x (pulled in by the Boot 3 upgrade) dropped this constraint entirely (confirmed no `SafeHtml` class in `hibernate-validator-8.0.1.Final.jar`, same finding as in the `egov-localization` and `egov-hrms` migrations). Adopted upstream's version of `Report.java`, which had already dropped it independently. `org.hibernate.validator.constraints.NotEmpty`/`.Email` (used in `Token.java`/`User.java`) are unaffected - confirmed both classes are still packaged in Hibernate Validator 8.
- **`BaseSMSServiceImpl.setupSSL()` migrated to Apache HttpClient 5**: Spring 6's `HttpComponentsClientHttpRequestFactory` only accepts an httpclient5 `CloseableHttpClient` (`org.apache.hc.client5...`), not the old httpclient4 type this method built (`org.apache.http.impl.client.CloseableHttpClient`) - would not have compiled under Boot 3. Rewrote using `PoolingHttpClientConnectionManagerBuilder` + `HttpClients.custom().setConnectionManager(...)`, following the exact pattern upstream's own (differently-structured) `BaseSMSService.java` already uses for Boot 3. The rest of the class (blacklist/whitelist checks, config-map-driven request body building, the `executeAPI` response parsing) is untouched fork logic.
- **`spring.kafka.consumer.value-deserializer=...ErrorHandlingDeserializer2`**: this class was renamed to `ErrorHandlingDeserializer` (dropping the "2") in spring-kafka 3.x (confirmed by inspecting the actual `spring-kafka-3.1.1.jar` pulled in by Boot 3.2.2 - only `ErrorHandlingDeserializer.class` is packaged). Startup failed immediately with `ClassNotFoundException` until fixed.

## Deliberately *not* changed

- **`NICSMSServiceImpl`'s request field names and SHA-512 key** (`content`/`mobileno`/`senderid`/`templateid`, plus a `hashSHA512(username+senderid+message+secureKey)` value sent as `&key=`): upstream's equivalent uses different field names (`message`/`mnumber`/`dlt_entity_id`/`dlt_template_id`) and no hash-key parameter at all. Traced via `git log -p` to a real, deliberate HP commit (`703627de4e`, following an initial base-integration commit `04e7f8e743`) - this is HP's actual production authentication handshake with the NIC/MSDG SMS gateway their `sms.provider.url` (`https://msdgweb.mgov.gov.in/esms/sendsmsrequestDLT`) is configured against, not something to reconcile with upstream's differently-configured gateway. Ported unchanged.
- **Property key names in `SMSProperties.java`** (`sms.provider.request.type`, `sms.provider.content.type`, `sms.verify.response.contains`, etc.): upstream renamed these to camelCase (`requestType`, `contentType`, `responseContains`) at some point after HP forked. Since this was an upgrade-in-place of the fork's own `SMSProperties.java` (not a replacement with upstream's), the fork's original dot-separated names were kept throughout - they already correctly match the already-configured `application.properties` values (including real production gateway credentials), so no rename was needed or made.
- **`UserServiceImpl.searchUserByNumber()`'s hardcoded `.tenantId("hp")`**: HP being a single-state deployment, this is consistent with `state.level.tenant.id=hp` used everywhere else in this service. Left as-is, just noting it's a hardcode rather than reading the configured tenant property.

## Environment note (not a code issue)

While investigating a wall of "cannot find symbol" errors on every Lombok-annotated class during a standalone `mvn compile`, found that this workspace's `mvn` was silently building under a stray **JDK 26** (Homebrew's unversioned `openjdk` formula had been upgraded since earlier in this session), not the JDK 17 this project targets - `java -version` on `PATH` correctly showed 17, but `mvn`'s own wrapper script falls back to `/opt/homebrew/opt/openjdk` (unversioned) whenever `JAVA_HOME` isn't set, and picked up 26 instead. Lombok 1.18.22 doesn't run under JDK 26, so annotation processing silently produced nothing, everywhere. `upyogctl` itself is unaffected - it sets `JAVA_HOME` explicitly in `.upyog.env` to the versioned `openjdk@17` - so this only bit direct, manual `mvn` invocations outside of `upyogctl start`. Worth keeping in mind for any future manual `mvn` command in this workspace.
